# E2E

Сквозные тесты Playwright поверх **собранного** приложения. Бэкенд не нужен:
`apps/web/public/config.json` → `useMocks: true`, и все сценарии идут на моках.

```bash
pnpm build              # e2e гоняются по dist, а не по dev-серверу
pnpm e2e                # оба проекта: desktop 1440 и mobile 390
pnpm e2e --project=desktop --reporter=line
pnpm e2e --ui           # интерактивный режим
pnpm e2e:install        # докачать Chromium (один раз)
```

Полный прогон — около минуты (33 теста, 4 воркера).

## Почему `vite preview`, а не `vite dev`

Репозиторий лежит на диске Windows (`/mnt/x`), inotify туда не доходит, и HMR в конфиге
включён опросом файлов (`vite.config.ts`, `server.watch.usePolling`). Под Playwright это
выливается в самопроизвольные перезагрузки страницы посреди теста. `preview` отдаёт
статику из `dist` и ничего не сторожит. Порт — 3120 (`E2E_PORT`), потому что 3000 на
машинах разработки занят.

Сервер поднимает сам Playwright (`webServer`). Локально он переиспользует уже
запущенный на этом порту, в CI — всегда поднимает свой.

| Спек           | Что проверяет                                                                    |

| `catalog`      | фильтры в адресе, сортировка, пустая выдача, сравнение до 4 позиций              |

## Правила

- **Селекторы — по ролям и тексту.** Цепочек CSS-классов нет. Единственное исключение —
  клетки кода `input[data-radix-otp-input]`: своего доступного имени по-русски у них нет.
- **Никаких `waitForTimeout`.** Ожидание — только по состоянию: `expect(...).toBeVisible()`,
  `toHaveCount(0)`, `expect.poll`. Переход в машине состояний заказа подтверждается
  исчезновением кнопки, а не появлением текста: названия всех ступеней и так напечатаны
  в списке «Ступени заказа», и поиск по тексту там всегда успешен.
- **Чистый контекст на тест.** Состояние моков живёт в `sessionStorage` (сессия) и
  `localStorage` (заказы, сравнение, SKU); Playwright даёт каждому тесту свой контекст.
  Сценарии, где состояние переходит от роли к роли (`roles-flow`, `seller-offer`), —
  один тест и `test.describe.configure({ mode: "serial" })`.
- **Метка `@mobile`.** Тесты с ней гоняются только в проекте `mobile` (390 px), остальные —
  только в `desktop`. Длинные сквозные сценарии проверяют логику, а не раскладку, и
  дважды их гонять незачем.

## Известные нарушения приложения

Они вынесены в точечные исключения, чтобы проверки работали на остальных маршрутах;
рядом с каждым — `TODO`. Чинить их должен код приложения, не тест.

- `smoke`: `/company` на 390 px даёт горизонтальную прокрутку 42 px (`KNOWN_OVERFLOW`).
- `a11y`: у `/account/orders` нет `<h1>` (`KNOWN_NO_H1`).

## Версия Playwright

`@playwright/test` — `^1.57.0`. С 1.58 Playwright перешёл на сборки Chrome for Testing,
которые качаются из `storage.googleapis.com`; в окружении разработки этот хост
недоступен, а сборки самого Playwright (`cdn.playwright.dev`, ревизия 1200) — доступны.
Если поднимать версию выше, нужно сначала проверить, что браузер скачивается.

## Чего здесь нет

`@axe-core/playwright` (MPL-2.0) не подключён: `a11y.spec.ts` обходится своими
проверками и сторонних зависимостей не тянет. Если понадобится полный аудит
(контраст, порядок фокуса, ARIA), пакет добавляется отдельным решением, а тест
имеет смысл сделать нестрогим — отчёт о нарушениях в артефакт, падение только на
`critical`.
