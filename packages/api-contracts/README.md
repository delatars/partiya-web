# @partiya/api-contracts

Типы контракта фронт ↔ бэк. Источник истины — `openapi.json` бэкенда
(`partiya-api`, ARCHITECTURE.md, 8.5): бэкенд собирает спецификацию из аннотаций
хендлеров, здесь она превращается в TypeScript.

В пакете **две** ветки типов, и это сознательно:

| Где                                                                  | Что                             | Кто использует                                |
| -------------------------------------------------------------------- | ------------------------------- | --------------------------------------------- |
| `src/*.ts` (`auth.ts`, `orders.ts`, `seller.ts`, `backoffice.ts`, …) | написаны руками                 | приложение (`src/index.ts` реэкспортирует их) |
| `src/generated/**`                                                   | сгенерированы из `openapi.json` | только сверка `src/contract-check.ts`         |

Рукописные типы описывают экраны целиком, включая поля, которых бэкенд ещё не
отдаёт (они помечены `?` и разделом «расширения фронта»). Сгенерированные —
ровно то, что API отдаёт сегодня. Чтобы эти две картины не разъехались молча,
между ними стоит **сверка на уровне типов**.

## Сверка контракта (`src/contract-check.ts`)

Рантайма в файле нет — одни объявления типов. Он существует ради `tsc`: как только
бэкенд разойдётся с фронтом, `pnpm typecheck` покажет операцию и поле.

```sh
pnpm typecheck                         # весь монорепозиторий, включая сверку
pnpm --filter @partiya/api-contracts typecheck
```

Файл лежит внутри `src`, поэтому попадает в `tsconfig` пакета сам; в `src/index.ts`
он намеренно **не** реэкспортируется — это проверка, а не часть публичного контракта.

Для каждой операции, которой приложение реально ходит по HTTP
(`apps/web/src/shared/api/http/*.ts`), проверяются две вещи:

1. **ответ** бэка присваивается рукописному типу фронта — значит бэк отдаёт всё
   обязательное, имена и типы полей совпадают (лишние поля бэка не мешают);
2. **тело запроса** фронта присваивается тому, что принимает бэк.

Покрыто 157 утверждений по 99 операциям из 117. Непокрытые — те, где сверять
нечего: SSE-потоки (`/me/stream`, `/orders/{id}/stream`), загрузка файлов
(`/uploads/{token}`), служебные `/healthz` и `/openapi.json`, ответы `void`
(`logout`, `revokeSession`, `deleteArtwork`) и операции, которых нет ни на одном
экране (`markOrderDelivered`, `replyToDispute`, `getQuote`, `catalogCategories`,
`getOrg`, `listEscrowDeals`, `getEscrowDeal`, `getSellerFunnel`,
`getLedgerReconciliation`).

### `null` против `?` (Q-141)

Бэк отдаёт `null` там, где рукописный тип объявил `?`. Рукописные типы **не
правятся**: вместо этого сверка нормализует стороны утилитой `Loose`. Свойство,
которое допускает `null` или `undefined` либо объявлено через `?`, считается
«необязательным, и `null` тоже годится»: `null` ≡ «поля нет».

Так проверка ловит то, что действительно ломает экран, — другое имя поля, другой
тип, отсутствующее у бэка обязательное поле, чужой `enum`, — и не спотыкается о то,
что бэк пишет `null`, а моки ключ не присылают. Остаточный риск записан в
QUESTIONS.md: код фронта везде читает такие поля через `??` / `?.`.

Нормализуется **только одна сторона** — цель присваивания. Это не украшение:
`tsc` при сравнении двух глубоко вложенных инстанцирований одного псевдонима
включает защиту от бесконечной рекурсии и считает их совместимыми, из-за чего
первая версия сверки молча пропускала расхождения глубже третьего уровня.
Когда псевдоним стоит только на цели, защита не срабатывает.

### Самотесты

Сама утилита проверяется в том же файле: совместимые пары обязаны компилироваться,
несовместимые — падать. Несовместимые помечены `@ts-expect-error`, поэтому если
проверка деградирует и такая строка станет валидной, `tsc` ругнётся на
неиспользованную директиву. Покрыты: переименованное поле, пропущенное обязательное,
`null` на месте обязательного, лишнее значение `enum`, другой тип вложенного поля,
расхождение на 4-м уровне вложенности и две ошибки в теле запроса.

### Известные расхождения (`Known<>`)

28 операций сверяются «по имени, но не по форме»: типы остаются связанными
(переименование или удаление любого всё равно валит сборку), но присваиваемость
не проверяется. У каждого исключения над строкой написана причина. Их всего три
вида:

- **`#[schema(value_type = Object)]` на бэке** — поле описано свободным объектом,
  хотя по проводу едет настоящая структура (`marks` и `review` приёмки, `params`
  и `delivery` образца, `headers`/`limits` билета загрузки, `channels` настроек
  уведомлений, `tranches` финансов, `promos` ранжирования, `ranking` сводки завода);
- **`#[serde(flatten)]` на бэке** — utoipa не раскрывает поля вариантов, и вместо
  размеченного объединения в схеме остаётся свободный объект (`EventDto` журнала
  заказа, `DraftDto` черновика SKU);
- **рекурсия** — дерево категорий (`children: Vec<Object>`), utoipa её не разворачивает.

Отдельно стоят `confirmTrancheFunds` и `confirmDealPayout`: бэк отдаёт сделку
`payments`, а экран ждёт пересчитанную сводку финансов. Привести можно только
перенеся маршрут в `backoffice` — `payments` не может зависеть от бэк-офиса (цикл
крейтов). Рантайму это не мешает: `AdminFinancePage` ответ не читает, а
инвалидирует запросы бэк-офиса.

Чего сверка **не** ловит сознательно: лишнее поле в теле запроса фронта —
структурная присваиваемость его пропускает, а serde на бэке неизвестные поля
игнорирует. Переименованное или пропущенное поле запроса ловится.

## Обновить типы

```sh
pnpm --filter @partiya/api-contracts generate
```

Скрипт (`scripts/generate.mjs`) берёт спецификацию и кладёт результат в
`src/generated/`. Источник выбирается так:

1. аргумент: `pnpm --filter @partiya/api-contracts generate ../../../partiya-api/docs/openapi.json`;
2. переменная `PARTIYA_OPENAPI`;
3. по умолчанию — `../../../partiya-api/docs/openapi.json`, снимок в соседнем
   репозитории, который коммитится вместе с кодом бэкенда.

Годится и живой сервер: `... generate http://127.0.0.1:8025/api/v1/openapi.json`.

Генератор — [`openapi-typescript`](https://openapi-ts.dev): только типы, никакого
рантайма в бандле. Выбран вместо `orval`, которому нужен Node ≥ 22.18, а в проекте
Node 20 (`.nvmrc`).

**Генерация идемпотентна:** повторный запуск без изменений в `openapi.json` не
меняет ни байта. Поэтому `src/generated` внесён в `.prettierignore` — формат этих
файлов задаёт генератор, и `prettier --write` ломал бы проверку «повторный
`generate` без диффа».

Оба файла в `src/generated/` **правятся только скриптом** — руками в них ничего не
дописывать, изменения перетрутся при следующей генерации. Менять надо аннотации в
`partiya-api` и заново собирать спецификацию:

```sh
cd ../partiya-api && cargo run -p partiya-api -- openapi --out docs/openapi.json
```

## Что внутри `src/generated/`

- `openapi.ts` — вывод генератора: `paths`, `operations`, `components`.
- `index.ts` — именованные псевдонимы, чтобы не писать `components["schemas"][…]`.

Типы запроса и ответа конкретной операции берутся из `operations`:

```ts
import type { operations } from "@partiya/api-contracts/src/generated";

type SearchQuery = operations["catalogSearch"]["parameters"]["query"];
type SearchResponse = operations["catalogSearch"]["responses"][200]["content"]["application/json"];
```

## Как добавить операцию в сверку

1. Убедиться, что экран действительно ходит этой операцией
   (`apps/web/src/shared/api/http/*.ts`).
2. Дописать в `contract-check.ts` строку в раздел своего домена:

```ts
export type GetThing = Response<C.Thing, Res<"getThing">>;
export type SaveThing = Request<Req<"saveThing">, C.SaveThingBody>;
```

3. Запустить `pnpm typecheck`. Упало — это и есть расхождение: чинить надо
   **бэкенд** (эталон — контракт фронта), а `Known<>` ставить только тогда, когда
   починить нельзя, и обязательно с причиной в комментарии над строкой.

## План перехода приложения на сгенерированные типы

1. **Сейчас:** приложение работает на рукописных типах, сверка держит их в
   согласии со спецификацией.
2. **Шаг 1.** Снять исключения `Known<>`: заменить на бэкенде
   `#[schema(value_type = Object)]` настоящими схемами, а `#[serde(flatten)]` —
   явными DTO. После этого сверка станет полной.
3. **Шаг 2.** Перевести `src/index.ts` на реэкспорт из `src/generated/index.ts`,
   оставив рукописные файлы только для того, чего в API нет (расширения фронта).
4. **Шаг 3.** Удалить дубликаты и включить генерацию в CI: спецификация изменилась
   → типы пересобираются → `pnpm typecheck` ловит ломающее изменение контракта
   (job `contracts-drift`, пока `continue-on-error` — Q-301).
